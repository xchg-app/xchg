# Команды

*English version: [../cli.md](../cli.md).*

Общая форма: `xchg <команда> [аргументы]`; `xchg help` печатает этот список коротко, `xchg help <команда>` (или `xchg <команда> --help`) — только строки этой команды.
Ошибки идут в stderr, код возврата `1` — ошибка, `2` — неверный вызов, `3` — `wait` не дождался письма, `4` — записано в локальный клон хаба, но отправить не удалось.

## Адрес

`[хаб:]часть[:часть]` — части можно писать в любом порядке:

| адрес | куда попадёт |
|---|---|
| `all` | `all/` — всем в хабе |
| `@api` | `projects/api/` — всем, кто на проекте |
| `bob` | `people/bob/` — человеку, заберёт любой его агент |
| `@api:bob`, `bob:@api` | `projects/api/bob/` — агенту: человек × проект |
| `me`, `@api:me` | вам самим и вашему агенту — так свои адреса подписывает `inbox` |

Человека можно называть логином, именем или алиасом из `contacts.md` (регистр не важен); логин
важнее чужого алиаса. Адресат должен быть в книге контактов: человеку, чью строку убрали, писать
нельзя, даже если его каталог и письма остались в хабе.
Хаб подставляется сам, если адрес однозначен: человека ищут в книгах контактов, поэтому `@api:bob`
уходит в тот единственный хаб, где bob есть в проекте api. Если один адрес есть в нескольких хабах —
очередь проекта, ваш собственный агент, вы как человек — клиент ничего не отправляет и печатает, кто
прочитает письмо в каждом хабе (`work (5 people), me (only you)`): уточните (`work:@api:bob`) или
выберите один раз для этого репозитория:

```bash
git config xchg.hub work      # адреса без префикса, подходящие нескольким хабам, идут сюда
```

Выбор локальный, на клон, как `xchg.project`; `xchg projects` помечает этот хаб `here*`, `xchg status`
печатает его, и туда же `projects add` без `--hub` заводит проект. Глобальный `default` в `xchg.conf`
действует только для `all` без префикса и для `projects add`.

Файлы адресуются так же: `work:projects/api/…md`, просто путь (если он однозначен среди хабов)
или абсолютный путь внутри клона.

## Читать

```bash
xchg inbox [--brief] [--all] [--history] [--max-age N] [--hub H]
xchg read <файл>
xchg seen [адрес | файл]
xchg mute <файл>...
xchg thread <файл>
xchg sent
```

`inbox` синхронизирует хабы (параллельно, общий таймаут 20 с) и показывает адреса **этой
сессии**: хаб целиком, вас как человека, ваш проект и вашего агента. Открытые задачи видны
всегда, сообщения — пока не прочитаны. Сообщения в других ваших проектах и ответы на письма других ваших агентов сворачиваются в одну
строку-счётчик; `--all` показывает их, `--history` добавляет прочитанные сообщения и заглушённые
письма. `--brief` — формат для хуков: при старте сессии он показывает всё открытое, в остальных
случаях — только то, что этому агенту ещё не показывали, поэтому повторный хук на то же молчит
(0 байт). У вывода хука есть бюджет: когда список длиннее `digest` строк (`xchg.conf`, по умолчанию 12),
задачи остаются построчно, а сообщения сворачиваются в одну строку на отправителя и адрес, со
счётчиком и последним заголовком. Строка сохраняет колонки ящика, поэтому `read`, `seen`
и `reply` принимают её как есть; `xchg seen <адрес>` снимает такую кучу, когда её посмотрели. Всё, что
стоит за дайджестом, считается показанным.

`read` печатает письмо и ничего не помечает: письмо, прочитанное в сессии, которая погибла, должно
дождаться следующей; напоминание о пометке он печатает на stderr. `reply` помечает письмо, на которое отвечает.
`seen` помечает сообщения прочитанными: без аргумента — все адреса этой сессии, иначе адрес или
один файл. Отметки у каждого агента свои и хранятся не в хабе, а локально: `.git/xchg-read/` в клоне хаба.

Новый агент (только что добавленный проект, свежий клон хаба, другая машина) не получает всю историю
хаба непрочитанной. При его первом `inbox` или `wait` в этом клоне сообщения старше суток в хабе, у вас
как человека и в ваших проектах один раз помечаются для него прочитанными; `inbox` говорит, сколько
(`--history` их покажет). Открытые задачи остаются на виду, а адрес самого агента не трогается: то, что
туда передали, предназначено ему.

`mute` — «не моё»: письмо в вашем общем адресе, которое должен разобрать другой агент (например,
задача вам как человеку, которую возьмёт агент другого проекта). Для этого агента оно пропадает
из `inbox`, счётчиков и хуков и больше не будит `wait`; в хабе ничего не меняется, остальные агенты
видят письмо как раньше. Если потом взять такую задачу себе через `claim`, пометка снимается.

`thread` собирает переписку по `re:`, включая закрытые задачи (их текст берётся из истории git).
`sent` показывает ваши открытые задачи — у сообщений нет закрытого состояния, их там нет. Задача,
на которую получатель ответил по `re:`, — `replied`, остальные — `waiting` и идут первыми: это и есть
настоящие долги. Само ничего не закрывается, ответ может быть вопросом или отказом: приняв результат,
закройте задачу сами через `xchg done <файл>` — отправитель может закрыть свою задачу.

## Ждать

```bash
xchg wait [--timeout сек] [--interval сек] [--all] [--hub H]
```

Блокируется и сам, без модели, раз в `--interval` секунд (по умолчанию 30) забирает изменения
хабов. Как только появляется письмо, которого этот агент ещё не видел — ни хуком, ни `inbox`,
ни прошлым `wait`, — печатает его в формате `inbox --brief` и выходит с кодом 0; по `--timeout` —
с кодом 3. Открытые задачи, свои письма и взятые через `claim` задачи повторно не будят.
Зачем и как этим пользоваться без человека — [autonomous.md](autonomous.md).

## Писать

```bash
xchg send <адрес> <slug> [--re файл] [--ref куда] [--attach файл]... < тело
xchg post <адрес> <slug> [--re файл] [--ref куда] [--attach файл]... < тело
xchg reply <файл> <slug> [--task] [--attach файл]... < тело
xchg forward <файл> <адрес> [--note «…»]
xchg attach <файл>... [--hub H]
xchg attachments <файл>
xchg get <файл | att:хеш/имя> [--to КАТАЛОГ] [--hub H]
```

`send` создаёт **задачу** (`kind: task`), `post` — **сообщение** (`kind: message`). `slug` —
короткое имя файла из `[A-Za-z0-9._-]`, тело читается из stdin. Необязательный `--ref` указывает,
где лежит актуальное состояние (репозиторий, файл, PR).

`reply` отвечает отправителю исходного сообщения — адрес и `re:` берутся из файла, промахнуться
хабом нельзя; ответ — сообщение, `--task` делает его задачей. Ответ на письмо этого же агента
(тот же человек и проект) идёт его получателю (`to` из файла), так что тред можно продолжить с любой
стороны; письму другого вашего агента отвечают этому агенту. Ответ на сообщение помечает
его прочитанным; задача остаётся открытой до `done`.
Письмо из репозитория, который не заведён проектом в хабе, подписывается только человеком, и ответ на
него придёт вам как человеку, а не этому агенту: клиент предупреждает об этом на stderr и подсказывает
`xchg projects add`.
`forward` копирует сообщение в другой хаб как новое от вашего имени с пометкой `forwarded_from`;
оригинал не трогается. Это единственный способ перенести сообщение между хабами.

Если хаб недоступен, сообщение записывается в локальный клон, а команда выходит с кодом `4`.
Его отправит ближайший `xchg sync`, `xchg inbox` или `xchg wait`, как только хаб ответит;
`xchg sync` сам выходит с кодом `4`, пока что-то остаётся неотправленным.
Если не удался сам локальный коммит (например, у git не заданы `user.name`/`user.email`), ничего
не записывается и не отправляется: команда выходит с кодом `1`, называет причину, а запись
откатывается, так что повтор её не дублирует.

`--attach` выкладывает файл в хаб до того, как пишется письмо, и добавляет ссылку на него
(`att:<хеш>/<имя>`) в строку `attachments:`; если хаб файл не принял, не отправляется ничего.
`attach` делает то же без письма и печатает ссылку, чтобы вставить её в текст. `attachments`
показывает, что приложено к письму и скачано ли; `get` скачивает файлы письма или одну ссылку в
`.git/xchg-att/` клона хаба (или в `--to`) и печатает пути. Как хранятся вложения —
[hubs.md](hubs.md#вложения).

Если тело похоже на токен или приватный ключ, клиент предупреждает, но отправляет. Вложения не
проверяются.

## Задачи

```bash
xchg claim <файл>
xchg done <файл>
```

`claim` переносит задачу в адрес вашего агента — это видно всем, и двое не сделают одну работу
дважды. Атомарность даёт git: кто первым запушил, тот и взял; проигравшему команда скажет, кто
успел, и откатит его локальный коммит. `done` закрывает задачу — файл уезжает в `done/` рядом
со своим адресом. К сообщениям обе команды не применяются.

## Люди и проекты

```bash
xchg who [запрос] [--hub H]
xchg contact [--name N] [--aliases «a, b»] [--contact C] [--hub H]
xchg contact rm <login> [--hub H]
xchg projects [--hub H]
xchg projects add [<имя>] [--repo <где код>] [--owner login] [--hub H]
xchg agent
```

`who` печатает книгу контактов хабов: строку каждого человека и проекты, на которых у него есть
агент (это выводится из каталогов, а не заполняется руками). `contact` без флагов печатает вашу
строку, с флагами — правит её и пушит; строка появляется сама при подключении к хабу.
`contact rm` убирает из книги чужую строку: человеку больше нельзя писать, а его каталоги
и письма остаются в истории. Свою строку так не убрать — для этого `xchg hub rm`. Книгу, как
и весь хаб, правит любой участник; хостинг хаба может отказать в такой правке строкой `xchg: …`.

Агент знакомится с книгой сам: её печатает `xchg hub add` и первый `inbox` нового агента в этом
клоне хаба (по строке на человека: логин, имя, алиасы, проекты). Дальше `inbox` — и хуки тоже —
одной строкой сообщает, кто пришёл, кто ушёл и чья строка изменилась, по разу на агента; о вашей
собственной строке вам не сообщают. `who` считается за просмотр книги, а отметка хранится локально
(`.git/xchg-contacts/` в клоне хаба), как отметки о прочтении.
`projects add` без имени заводит текущий репозиторий (имя проекта = имя репозитория) и создаёт
карточку `README.md` с `origin` клона в строке `Repository:`; по этой строке другие клоны кода находят
проект (см. [agents.md](agents.md)). На существующем проекте `--repo` обновляет строку `Repository:`
в карточке — так чинят карточку после переезда кода. `agent` печатает ваши адреса в этой сессии — по
одному на хаб, где заведён этот проект.

## Хабы

```bash
xchg hubs
xchg hub init <имя> [--remote URL] [--path P] [--login L] [--ssh-key K]
xchg hub add <имя> <remote> [--login L] [--path P] [--ssh-key K]
xchg hub key <имя> <путь к ключу>
xchg hub check <имя>
xchg hub upgrade <имя> [--contract]
xchg hub rm <имя>
xchg hub remote <имя> <url>
xchg key new [--name N]
xchg sync [--hub H] | xchg log [n] [--hub H] | xchg status | xchg install | xchg version
```

Хаб, который есть в `xchg.conf`, но не склонирован по своему `path` (конфиг перенесён с другой
машины, клон удалён), исключается из всех команд, кроме `hub`, `hubs` и `status`: в его каталог
ничего не пишется. `inbox` называет его (в хуке — при старте сессии), `sync` называет и завершается
с кодом 1, `status` показывает `NO CLONE`. Каждая подсказывает команду, которая это исправляет:
`xchg hub add <имя> <remote>` с зарегистрированным remote клонирует хаб в зарегистрированный путь,
сохраняя его логин и ключ.

`hub upgrade` приводит собственные файлы хаба к версии клиента: `README.md` с правилами,
`.gitattributes`, каталоги `all/` и `projects/`. Сообщения, `contacts.md` и паспорта не трогает.
Если хаб уже в актуальном виде, ничего не пишет. Иначе — один коммит `[hub] upgrade to <версия>`
и push, как любая запись (код 4, если хаб недоступен). Команда отказывает и оставляет хаб как есть,
если правила хаба пришли от более нового клиента или его контракт новее клиентского. Хаб на старом
контракте переходит на новый только с `--contract`: после этого клиенты старого контракта писать
в него перестают.

## Переменные окружения

| | |
|---|---|
| `XCHG_HUB` | хаб по умолчанию для команд с `--hub` |
| `XCHG_CONF_DIR` | каталог конфига вместо `~/.config/xchg` |
| `XCHG_MAX_AGE` | дебаунс синхронизации в секундах |
| `XCHG_READ_GRACE` | насколько свежие сообщения новый агент ещё видит непрочитанными, в секундах (86400) |
| `XCHG_NO_SELFUPDATE=1` | не обновлять клиент |
